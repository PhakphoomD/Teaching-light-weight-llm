# T2.2 — Extend the Registry Pattern to Every Slot

- **Phase:** P2 (code) · **Owner:** codebase-steward · **Depends on:** T2.1
- **Output:** `MemoryRegistry`, `PresetRegistry`, `JudgeRegistry` (+ `ArmRegistry` if EVAL_SPEC
  models arms as strategies) + tests

## Objective
Generalize the existing provider factory pattern so every config slot resolves through a
registry — the plugin seams the user asked for ("เปลี่ยนโมเดล/memory ได้เหมือนตัวต่อ").

## Why (hub context)
`src/providers/factory.py` already does this perfectly for models (slot A/B). Slots C/D/F are
hardcoded inside the 843-line legacy loop. After this task: adding a new memory backend or
prompt preset = write class + `@register("name")`, zero runner edits.

## Read first
- `src/providers/factory.py` (the pattern — copy it, don't reinvent)
- structure.md v2 seams table (T1.2) · schema.md contracts (T1.1, T1.3) · EVAL_SPEC (T1.4)

## Steps
1. One small generic registry helper (or per-domain copies if simpler — steward's call,
   consistency over cleverness).
2. Define the interfaces from structure.md seams: `MemoryBackend` (T1.3 methods),
   `PromptPreset` (render first/refine/critique from template names), `Judge` (score(q, answer)
   → verdict), `ArmStrategy` if applicable.
3. Register initial implementations as THIN placeholders where the real block lands later
   (`none` memory backend is real and trivial: stores nothing, retrieves nothing — arm A/B need it).
4. Tests: unknown name → clear error listing registered options; registration collision → error.

## Definition of Done
- All slots resolvable from a validated config to a concrete object; tests pass (evidence).
- Adding a dummy backend in a test file requires zero changes outside that file.

## Must NOT do
- Don't implement real FAISS/judge logic here (T2.5/T2.3). Don't refactor providers/ beyond
  what reuse requires. Legacy loop untouched.
