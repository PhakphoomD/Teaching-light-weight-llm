# T3.10 — Retriever upgrade ladder, ranked by OFFLINE hit-rate (cheap de-risk) → GATE

- **Phase:** P3-E (code) · **Owner:** data-engineer · **Depends on:** T3.9
- **Output:** 2–3 retriever variants + an offline hit-rate@k table + a go/no-go for T3.11

## Objective
Build a small ladder of stronger retrievers over the SAME WixQA KB and rank them purely by
**offline hit-rate@k** (did the gold KB article land in top-k for each of the 200 questions) —
NO LLM generation, NO judge calls. This is the cheap step that decides whether the expensive
end-to-end run (T3.11) is worth running, and with which retriever.

## Why (hub context)
Hit-rate is measurable offline in seconds with zero API cost — so measure it BEFORE spending a
3-seed end-to-end run. This is the T2.7-pilot discipline applied to retrieval: de-risk offline
first. The ladder also gives ≥3 hit-rate points for the dose-response curve (T3.11).

## Read first
- T3.9 retrieval-log harness + the 55% MiniLM/whole-article baseline (variant #1)
- `scripts/wixqa_build_index.py` · `tools/rag/` + `src/tlw/memory` (FAISS) · `data/rag/wixqa_kb/`
- memory [[wixqa-rag-positive-result]] limits (named levers: chunking / encoder>MiniLM / hybrid)

## Steps
1. Implement variants over the 6,221-article KB (KB-only, seal re-verified each rebuild):
   - **V2 — chunking:** split long articles into passages; index at chunk granularity; map chunk→article.
   - **V3 — stronger encoder:** replace MiniLM (all-MiniLM-L6-v2, 384d) with a local off-the-shelf
     stronger sentence encoder (candidates: BAAI/bge-small/base-en-v1.5, intfloat/e5-base-v2,
     thenlper/gte-base — pick one or two, all run locally). Note query/passage prefix conventions
     (e5/bge need them) or hit-rate will silently drop.
   - **V4 — hybrid:** BM25 (lexical, `rank_bm25`) + dense fusion (RRF or weighted) — catches
     exact-term matches MiniLM misses.
2. For each variant + the T3.9 baseline, compute **hit-rate@k** (gold article in top-k; k = the
   RAG top-k, default 3) and hit-rate@{1,5,10} for shape, over all 200 questions. One table.
3. Optional cheap add: a cross-encoder re-ranker on top of the best dense retriever (still no LLM
   generation).
4. **GATE decision (record it):** if ≥1 variant beats the 55% baseline hit-rate meaningfully →
   pick the best 1–2 for T3.11. If NONE beats it → STOP and report "retriever ceiling on this KB"
   as the honest finding (the law still stands; the lever just has a practical ceiling here).

## Definition of Done
- Hit-rate@k table across baseline + ≥2 variants (200 questions each); KB-only seal re-verified;
  an explicit go/no-go naming which retriever(s) advance to T3.11 (or the stop-finding).

## Must NOT do
- No end-to-end LLM runs here (offline hit-rate only — keep it cheap). Don't tune the retriever
  against individual QA content (§0.2 — you may use gold *article ids* for hit-rate scoring, never
  the QA answer text to pick chunks). Don't index the expert QA answers.
