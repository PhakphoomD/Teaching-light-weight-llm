# T0.3 — Ground-Truth Leakage Census (map every leaking pipe)

- **Phase:** P0 (read-only) · **Owner:** qa-engineer · **Depends on:** none
- **Output:** `docs/audit/LEAKAGE_CENSUS.md`

## Objective
Enumerate EVERY path by which the reference answer (ground truth) can reach the student,
the memory store, or the score — with file:line — so P2 can seal each one with a test.
Do not fix anything; this is the demolition survey for §0.2.

## Why (hub context)
ADR-001: reported gains (25%→83%→100%) are inflated because GT leaked into the student and
memory ("P6C 100%" = the system retrieved the answer key it had stored). The last rebuild
missed leak paths because nobody listed them first. This census is the checklist that makes
the Track-A rebuild trustworthy.

## Steps
1. Grep for `ground_truth` across all live code + prompt templates; classify each hit:
   `STUDENT-VISIBLE` / `MEMORY-STORED` / `SCORE-PATH` / `TEACHER-ONLY (allowed)` / `LOG-ONLY`.
2. Trace each STUDENT-VISIBLE and MEMORY-STORED path end-to-end (trigger condition → prompt →
   storage → later retrieval) and document the loop hole it creates.
3. Audit score path: which metric components see GT (semantic_sim, rouge, exact, comparison
   judge) and what fraction of `final_score` weight they carry (compute from real config).
4. Audit artifacts: leakage-bearing files under `logs/experiments/` (e.g. GT-as-feedback
   memory stores) — list, don't touch.
5. Produce the census table: ID · path · file:line · class · severity · "how P2 must seal it".

## Definition of Done
- Census table where every `ground_truth` reference in live code is classified.
- Explicit statement of which paths are LEGAL (teacher feedback generation per §0.2) vs illegal.
- Seal-requirements list consumable by T2.3/T2.4/T2.5 as test cases.

## Must NOT do
