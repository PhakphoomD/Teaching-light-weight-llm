# T3.14 — Loop+RAG capstone: self-refine + RAG (the actual system, finally run together)

- **Phase:** P3-E (run + analysis) · **Owner:** ops-engineer + qa-engineer · **Depends on:** T3.11 (best retriever)
- **Runs before:** T3.12 (write-up) · **Output:** self-refine+RAG results on WixQA + the system-integration finding

## Objective
Run **self-refine + RAG together** on WixQA — the configuration the project is named after
(Loop+RAG) and that has NEVER been evaluated. Measure whether iterating (self-refine) on top of
retrieved context adds value where RAG alone leaves headroom — specifically **completeness
(pass@≥4)** and **reliability** on the **gold-retrieved** subset.

## Why (hub context — this closes a real scope gap, not scope creep)
Every RAG run to date was `arm: A, max_rounds: 1` — single-pass, NO loop (grep: all
`experiments/*RAG*.yml`). The loop (arm B self-refine) was only ever run WITHOUT RAG (Track A).
So Loop-alone and RAG-alone are measured; **Loop+RAG is not** — even though `RAG_SPEC.md:381-384`
flagged it as what "the *product* likely wants" and recommended it (never executed; the T3.5 gate
went to the retriever instead). The two components target DIFFERENT failure modes: RAG fixes
"missing knowledge", self-refine fixes "has the facts but the answer is incomplete/messy". WixQA
shows exactly this open door: gold-retrieved reaches pass@≥3 **0.409** but **pass@≥4 (complete)
stays ~0** ("a 3B + 1 article can't be as complete as the expert answer", [[wixqa-rag-positive-result]]).
That ~0 completeness floor is the failure mode self-refine exists to attack. This is the arm that
makes the portfolio about *the system*, not two separate studies.

## Steps
1. Build the Loop+RAG path: self-refine rounds (arm B, max_rounds 3, blind self-critique — student
   critiques its OWN answer, never sees gold, §0.2) ON TOP OF RAG grounding from the T3.11 winning
   retriever. Either extend `scripts/wixqa/run_rag.py` with a self-refine loop or run WixQA through the
   `run.py` arm-B + `memory.type: rag` pipeline — whichever is the smaller honest change.
2. **Verify grounding persists across refinement rounds** (implementation check): T3.3 wired
   grounding into the FIRST attempt only. Self-refine must keep the retrieved passages available in
   rounds 2–3 (refine the *grounded* answer, don't drift off it). If the code drops passages after
   round 1, fix that or document it — it materially changes the result.
3. Run seeds {13,42,123}, holding retriever/judge/student/top-k FIXED vs T3.11 (only the loop is
   added). Report pass@≥3 AND **pass@≥4**, split by gold-retrieved vs gold-missed.
4. **The finding (both outcomes valid, §0.1):**
   - Headline compares: RAG-only (T3.11) vs RAG+self-refine, with CI — overall and on the
     gold-retrieved subset, at BOTH bars. The key question: does self-refine lift **pass@≥4
     completeness** where knowledge is present (gold-retrieved)?
   - If yes → the system's two legs compound (RAG=knowledge, self-refine=completeness) — the
     product story. If no → self-refine does not compound with RAG here (self-refine can't improve
     what retrieval already delivered) — equally honest, and it sharpens the "retrieval is the
     bottleneck" law.
5. Cost/latency note (self-refine adds rounds → the product trade-off).
